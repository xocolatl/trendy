# A0070: what a database's definition can't say

A database is a variable that outlives the program, whose value is its
relvars together (TTM's dbvar, RM Prescription 16). Its units add each
relvar, `var kitchen.pantry: …`, and each constraint,
`constraint kitchen.stocked := …;`, in which its relvars are named alone:

```trendy
database kitchen;

var kitchen.pantry: relation { item: text, grams: integer } key { item };
var kitchen.recipes: relation { recipe: text, item: text } key { recipe, item };

constraint kitchen.stocked := is_empty{r: pantry where grams < 0};
constraint kitchen.known := recipes{item} <= pantry{item};

operator main{} [];
```

A database holds relvars, and nothing else; a relvar's type is written,
and it has no initial value, as its value is the database's, which
outlives every program, and the fix removes one:

```trendy,error
database kitchen;

var kitchen.pantry: relation { item: text } := relation { { item: "teff" } };
var kitchen.count: integer;

operator main{} [];
```

A database's constraint mentions its relvars alone (RM Prescription 23):
it holds for every program that uses the database, which none could check
of another program's variables. Its relvars are named alone in it, without
the database's name:

```trendy,error
database kitchen;
var stock := 5;

var kitchen.pantry: relation { item: text, grams: integer } key { item };

constraint kitchen.stocked := is_empty{r: kitchen.pantry where grams < 0};
constraint kitchen.enough := stock > 0;

operator main{} [];
```

A database isn't a value: it is declared, with its relvars and
constraints, for its definition, which its catalog records, and no
statement reads one yet:

```trendy,error
database kitchen;

operator main{} [
    call debug_value{v: kitchen};
];
```
